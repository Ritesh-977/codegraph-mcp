# codegraph-mcp — Project Overview

## Summary

`codegraph-mcp` is a Knowledge Graph MCP Server that gives LLM clients durable, queryable access to the structural dependencies of any GitHub repository. It operates as a two-process system: an offline CLI ingests repos by cloning, parsing via Python's `ast` and tree-sitter, and loading nodes and edges into Neo4j, while a FastMCP stdio server exposes that graph through six read-only tools to any MCP host. Ingestion and serving are strictly separated so the server never mutates data and never runs parsing code. Each repository is isolated under a unique `graph_id` that is enforced in every Cypher statement, allowing many repos to coexist in one database safely. Unresolved imports and calls are captured as `Symbol` leaf nodes rather than phantom files, keeping the graph honest about what it actually knows. Pruned files are handled with soft-delete tombstones instead of destructive deletes. The server emits LLM-readable error messages so tool failures degrade gracefully in a conversational context. Together these properties let a developer ask natural-language impact questions—like what breaks if `auth_service.py` changes—and receive accurate, graph-traversed answers without cloning anything locally. By persisting code structure in a traversable graph, it solves the problem of LLMs losing cross-session context and needing to re-read entire repos to reason about architecture.

## The Problem

Modern development rarely lives in a single repository. A feature touches a service, its shared library, a types package, and a downstream consumer — spread across repos owned by different teams. When you ask "what breaks if I change `auth_service.py`?", the honest answer requires tracing imports, calls, and type definitions through dozens of files in several repos. Developers answer this today with grep, IDE "find references," and sequential reading: slow, error-prone, and bounded by whatever their local checkout happens to include. There is no shared, queryable representation of how code actually connects across repositories.

LLMs make this worse, not better. Every new session starts from zero — the model re-derives the same facts, forgets connections it reasoned about an hour ago, and contradicts itself across turns. Dumping a whole repo into the context window doesn't help: real repos have thousands of files, context windows don't fit them, and even if they did, a flat file dump is not something an LLM can reliably traverse. What the model needs is *structured relationships* — a graph it can walk edge by edge, the way a database query walks joins — not a wall of text it has to re-parse on every question.

No durable, traversable representation of code architecture exists for LLMs today. An agent can read a file on demand, but it cannot, in a single structured operation, follow an edge from "this function" to "every caller across three repos." And without a shared store where multiple repositories' code graphs coexist, cross-repo reasoning is effectively impossible: the LLM working on repo A has no visibility into repo B's structure at all.

`codegraph-mcp` exists to close that gap. It builds and maintains a knowledge graph of code — files, symbols, imports, calls, and definitions, spanning repositories — and exposes it through the Model Context Protocol so any LLM agent can query impact, dependency, and structure programmatically rather than rediscovering them from raw text every time.

## The Solution

The solution is a three-phase, process-split architecture that turns a repository's code structure into a traversable Neo4j graph and exposes it to any LLM through the open Model Context Protocol (MCP).

**Phase 1 — Ingestion (offline CLI).** A standalone command, `codegraph ingest <url>`, accepts any GitHub repository URL and performs a shallow `git clone`. It then walks the file tree, honoring `.gitignore`, and parses each Python file with the stdlib `ast` module and each JavaScript/TypeScript file with tree-sitter. From each file it extracts only the code's skeleton: which files exist, which functions and classes each file defines, which files import which, and which functions call which. A single `git log` pass captures per-file commit metadata (last author, last commit date). All of this is written to Neo4j as a graph: `Repository` nodes `[:CONTAIN]` `File` nodes; files `[:DEFINE]` `Function` nodes; files `[:IMPORT]` other files; and functions `[:CALL]` other functions. Imports or calls that resolve outside the repository — stdlib modules, npm packages — become lightweight `Symbol` leaf nodes, so the graph records that the dependency exists without inventing phantom files. Every node and edge carries a `graph_id` equal to the repo slug (`owner/name`), which lets multiple repositories coexist in one Neo4j database with zero cross-talk. Re-ingestion is idempotent: changed nodes are upserted via `MERGE`, and files removed from the working tree are soft-deleted (tombstoned) rather than hard-destroyed.

**Phase 2 — The MCP Bridge (FastMCP stdio server).** A separate, read-only FastMCP server speaks the Model Context Protocol over stdio and exposes six tools — `list_repos`, `init_repository_node`, `get_repo_structure`, `find_file_dependencies` (the flagship: walks imports in both directions plus calls up to N hops, returning real in-repo files alongside a separate list of external symbols), `search_nodes`, and `get_node_detail` — plus two resources (`codegraph://repos` and `codegraph://schema/{graph_id}`). Every tool runs parameterized Cypher against the shared Neo4j, scoped by `WHERE n.graph_id = $graph_id`. The server never clones, parses, or writes; it holds no graph state in memory and re-queries the database on every tool call. Tool schemas auto-derive from pydantic type hints, so there are no hand-written JSON Schemas to maintain. Errors are designed to be LLM-readable: malformed arguments surface as JSON-RPC `-32602` (handled automatically by the SDK's pydantic integration), and business errors such as an unknown repo or missing file return `isError:true` with plain-text "what to do next" guidance, letting the LLM self-correct on retry.

**Phase 3 — Interaction (any MCP host).** Any LLM client that implements MCP — Claude Desktop, opencode, Cursor, or a custom client — spawns the server as a subprocess via a simple `mcpServers` config entry. The developer asks a question in natural language ("What files will break if I modify `auth_service.py` in repo A?"). The LLM first reads the `codegraph://repos` resource to ground itself, calls `init_repository_node` to confirm the repo exists, then calls `find_file_dependencies` with the file path. The server traverses the Neo4j graph and returns the exact subgraph of dependent files and functions (plus any external symbols), and the LLM reasons over that structured result to answer accurately — without ever downloading the repository to the developer's machine.

**Why this works.** The design rests on four choices. Neo4j's graph model matches the problem shape: multi-hop dependency traversal is Cypher's native strength, so `find_file_dependencies` is a single query rather than recursive application code. MCP gives the LLM a standardized, structured interface instead of ad-hoc file-reading, so the model receives clean, bounded answers rather than raw source it must re-parse. The process split keeps the server sandboxed and fast — no git, no disk writes, no risk of timeouts on long clones — because all heavy work lives in the offline ingest phase. And per-repo `graph_id` isolation, enforced in every Cypher statement, means the LLM cannot accidentally leak across repositories; it is a server-side guarantee, not client trust.
